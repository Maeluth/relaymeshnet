# Protocol Versioning & Compatibility 🔴 Core

> **Core.** Без версионирования и обратной совместимости обновления ломают сеть. Capability negotiation и три профиля — это протокольный уровень, не приложение.

## Принцип

Протокол RMN проектируется с расчётом на десятилетия эволюции.
Новые версии должны быть обратно совместимы. Старые узлы не должны ломаться
при получении сообщений от новых. Это не IPv4→IPv6 — у нас нет смены адресного
пространства. PeerID = SHA256(pubkey)[0:16] навсегда.

## Версионирование

### Wire Format

```
┌──────────┬──────────┬──────────┬──────────┬───────────────┐
│ Magic    │ Version  │ Type     │ Length   │ Payload       │
│ 4 bytes  │ 2 bytes  │ 2 bytes  │ 2 bytes  │ 0..65535      │
│ "RMN\x01"│          │          │ big-end  │               │
└──────────┴──────────┴──────────┴──────────┴───────────────┘

Version: 16-bit, начиная с 1
  v1: текущая спецификация (17-protocol-spec.md)
  v2-v65535: будущие версии
```

### Правила эволюции протокола

| Можно | Нельзя |
|---|---|
| Добавлять новые поля в конец структуры | Менять семантику существующих полей |
| Добавлять новые message types | Удалять существующие message types |
| Добавлять новые capabilities | Менять размер существующих полей |
| Deprecate поля (игнорировать, но не удалять) | Требовать новые поля от старых узлов |
| Добавлять reserved-байты для будущего использования | Менять порядок полей |

### Обработка неизвестных полей

```
Старый узел получает сообщение от нового (version > своя):
  1. Читает заголовок (Magic, Version, Type, Length)
  2. Если Version > своя: читает известные поля, игнорирует новые
  3. Если Version > своя И неизвестный Type: отправляет NOT_SUPPORTED
  4. НЕ падает. НЕ отключается. Просто не обрабатывает неизвестное.

Новый узел получает сообщение от старого (version < своя):
  1. Использует старый формат для этого узла (из HELLO)
  2. Не отправляет фичи, которых нет в capabilities старого узла
```

## Capability Negotiation

### HELLO Handshake

```
При первом контакте двух узлов:

A → B: HELLO {
  Version:    1,
  PeerID:     A_peerID,
  PubKey:     A_pubkey,
  PoHProof:   ...,
  Caps:       ["chat", "confirm_n", "x3dh", "file_transfer", "storage"],
  Signature:  Ed25519(A_priv, HELLO)
}

B → A: HELLO {
  Version:    1,
  PeerID:     B_peerID,
  PubKey:     B_pubkey,
  PoHProof:   ...,
  Caps:       ["chat", "confirm_n"],
  Signature:  Ed25519(B_priv, HELLO)
}
```

### Capability Strings

```
Базовые (все узлы):
  "ping"           — проверка доступности
  "chat"           — текстовые сообщения
  "confirm_n"      — confirm-N relay

Расширенные:
  "x3dh"           — X3DH + Double Ratchet (E2E)
  "file_transfer"  — отправка файлов > 2 KB
  "dht_store"      — хранение DHT-записей
  "storage"        — хранение контентных чанков
  "service_host"   — хостинг веб-сервисов
  "bridge"         — мост во внешнюю сеть
  "gossip"         — распространение репутации
  "transfer"       — перевод RELAY между кошельками
```

### Проверка совместимости

```
Перед отправкой сообщения:
  1. Проверить peer.Caps
  2. Если требуемая capability отсутствует:
     → Для chat/confirm_n: отправить (базовые, есть у всех)
     → Для x3dh: использовать NaCl box вместо X3DH
     → Для file_transfer: отклонить, сообщить пользователю
     → Для storage: не использовать этот узел для хранения
```

## Три профиля узлов

| Профиль | Caps | Железо | Размер бинарника |
|---|---|---|---|
| **Minimal** | `ping`, `chat`, `confirm_n` | Роутер 64MB RAM | ~2 MB |
| **Standard** | + `x3dh`, `file_transfer`, `dht_store`, `gossip`, `transfer` | Роутер 128MB RAM | ~5 MB |
| **Full** | + `storage`, `service_host`, `bridge` | ПК/ноутбук, 512MB+ RAM | ~12 MB |

Minimal-узел релеит трафик, зарабатывает RELAY, может отправлять текст.
Standard-узел делает всё что Minimal + файлы + E2E + DHT + переводы.
Full-узел делает всё + хостинг + контент-слой + bridge.

Все три профиля **совместимы** друг с другом. Full-узел не падает если
Minimal-узел не поддерживает storage. Minimal-узел не падает если
получил неизвестный message type от Full-узла.

## Deprecation Lifecycle

```
v1 → v2: поле X объявлено deprecated, но всё ещё обрабатывается
v2 → v3: поле X игнорируется (старые узлы v1 его ещё шлют, новые не читают)
v3 → v4: поле X удалено из спецификации (узлы v1 к этому времени вымерли)

Минимальное время между deprecation и удалением: 1 год
(столько живёт поколение пользователПользователстудентов в кампуси)
```

## Reserved поля

```
Каждая структура содержит reserved-байты:

OnionPacket:    [Version:1][HopCount:1][Reserved:2][...]
DHTMessage:     [Type:2][Reserved:2][SenderID:16][...]
PoRReceipt:     [RelayPeerID:16][Reserved:4][BytesRelayed:8][...]

Reserved = 0x0000 в текущей версии.
В будущих версиях можно использовать для флагов/расширений.
Старые узлы проверяют Reserved == 0 (для своих структур),
игнорируют Reserved в структурах от новых узлов.
```

## Пример: v1 узел получает v2 сообщение

```
v2-узел отправил OnionPacket с [Version:2][HopCount:1][Reserved:0x0003][...]
  Reserved=0x0003 во v2 означает "использовать сжатие LZ4"

v1-узел:
  1. Version=2 > 1 → OK, обрабатываем
  2. Читает HopCount (поле на том же месте, семантика не изменилась)
  3. Reserved=0x0003 — v1 не знает этот флаг → ИГНОРИРУЕТ
  4. Расшифровывает HopData (формат не изменился)
  5. Не использует LZ4-сжатие (v1 не умеет)
  6. Релеит пакет дальше как обычно

Результат: v2-фича (сжатие) не работает при проходе через v1-узел,
но пакет НЕ отброшен. Связь не нарушена.
```

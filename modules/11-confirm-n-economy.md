# L5: Confirm-N Economy 🟡 Required

> **Required.** Без confirm-N новичок с нулевым балансом не может отправить ни одного сообщения. Экономика не запускается — deadlock. Это bootstrap-механизм, без которого сеть не стартует.

## Проблема

В onion-сети каждое сообщение создаёт ×3 relay-нагрузки (3 hop'а).
Если relay всегда оплачивается RELAY-кредитами, новичок с нулевым балансом
не может отправить ни одного сообщения. Нужен механизм, позволяющий
зарабатывать кредиты СЕЙЧАС за счёт выполнения relay-работы СЕЙЧАС.

## Два уровня

```
Уровень 1 — Confirm-N (бесплатный, обязательный):
  Для сообщений ≤ 2 KB.
  Отправитель релеит N чужих пакетов → отправляет своё.
  Оплата = электричество на relay.
  Не тратит RELAY credits. Зарабатывает reputation + эмиссию кредитов (см. `13-hybrid-economy.md`).

Уровень 2 — RELAY credits (платный, опциональный):
  Для любых сообщений (включая файлы любого размера).
  Отправитель тратит RELAY с баланса.
  Цена = hops × размер × SEND_COST.
  Быстрее, не требует confirm-N.
```

## Формула динамического N

N подстраивается под размер сообщения и количество hop'ов:

```
N = max(2, ceil(hops × message_bytes / RELAY_CHUNK_SIZE))

RELAY_CHUNK_SIZE = 512 байт (стандартный relay-пакет)
```

| Сообщение | Байт | Hops | N | Комментарий |
|---|---|---|---|---|
| "Привет" | 50 | 3 | max(2, ceil(150/512)) = **2** | Минимум |
| "Длинное сообщение" | 1000 | 3 | max(2, ceil(3000/512)) = **6** | 6 relay-пакетов |
| Фото 5 МБ | 5000000 | 3 | max(2, ceil(15M/512)) = **29297** | Абсурдно → Уровень 2 |
| Файл 50 МБ | — | — | → | Только Уровень 2 |

Для файлов confirm-N бесконечно дорог → автоматический переход на RELAY credits.

## Confirm-N и onion-цепи: откуда берутся чужие пакеты?

При confirm-2 отправитель релеит 2 чужих relay-пакета. Откуда они?

```
Каждый узел поддерживает relay-очередь — буфер пакетов, ожидающих relay.
Пакеты попадают в очередь двумя путями:
  a) От соседей (onion-трафик, который этот узел должен переслать дальше)
  b) От broadcast/gossip (общая очередь сети)

При confirm-N:
  1. Узел берёт N пакетов из relay-очереди
  2. Релеит их (тратит электричество)
  3. Получает PoR-квитанции от следующих hop'ов
  4. Отправляет своё сообщение
```

## Низкая активность: что если релеить нечего?

```
Проблема: ночью 10 узлов онлайн, никто не отправляет сообщения.
→ Relay-очередь пуста. Confirm-N нечего релеить.

Решение 1: Dummy-трафик.
  Узлы периодически генерируют пустые relay-пакеты (padding-пакеты).
  Они не несут полезной нагрузки, но поддерживают очередь.

Решение 2: Adaptive N.
  Если relay-очередь пуста → N=0 (confirm не требуется).
  Узел отправляет бесплатно.
  При росте очереди → N возвращается к формуле.
```

## Высокая активность: приоритеты в очереди

```
Когда relay-очередь переполнена, приоритет:
  1. Срочные пакеты (отправитель заплатил RELAY credits)
  2. Confirm-N пакеты (отправители зарабатывают право отправки)
  3. Dummy-трафик (заполнитель, lowest priority)
```

## Экономическая петля

```
1. Новичок (баланс 0):
   → Хочет отправить "Привет" (50 байт, 3 hop'а)
   → N=2: релеит 2 чужих пакета (каждый ~512 байт)
   → Отправляет своё
   → Заработал +2 PoR + эмиссию кредитов → reputation растёт, баланс > 0

2. Новичок через неделю (баланс 0, reputation 3.5):
   → Хочет отправить фото 5 МБ
   → N=29297: слишком много → переходит на Уровень 2
   → Но баланс 0, RELAY нет
   → Тратит reputation в кредит: берёт в долг до CREDIT_LIMIT=70 (20×sqrt(3.5))
   → Отправляет, уходит в минус
   → Должен релеить, чтобы выбраться из минуса

3. Активный relay-узел (баланс 150, reputation 12.0):
   → Отправляет что угодно через Уровень 2, платит RELAY
   → Не делает confirm-N (уже заработал)
   → Может продавать RELAY на бирже новичкам
```

## Связь с tokenomics

```
Новичок: CREDIT_BASE = 0 (не получает бесплатных кредитов!)
  → Может отправлять ТОЛЬКО через confirm-N
  → Не может взять в долг (CREDIT_LIMIT = 0)

После confirm-N: reputation начинает расти
   → CREDIT_LIMIT = 20 × sqrt(reputation) ≈ 20 × sqrt(3.5) ≈ 37
  → Можно брать в долг до этого лимита
  → Но для возврата долга нужно релеить

RELAY credits зарабатываются:
  a) Через confirm-N — косвенно (reputation даёт credit line)
  b) Через relay чужих пакетов (когда узел — посредник в onion-цепи) — напрямую
  c) Через покупку на бирже
```

## Интеграция с onion routing

```
При отправке сообщения:
  1. Если размер <= 2KB и hops <= 5:
     → Confirm-N (если нужно), затем отправка
     → RELAY credits не тратятся
     → SEND_COST не применяется
  
  2. Если размер > 2KB:
     → Только через RELAY credits
     → Цена = hops × размер × SEND_COST (1 credit/KB/hop)
     → Проверка: balance >= цена

  3. Если баланс < цена, но размер <= 2KB:
     → Нужно confirm-N
     → N рассчитывается по формуле
```

## Параметры

| Параметр | Значение | Описание |
|---|---|---|
| `CONFIRM_THRESHOLD` | 2 KB | Максимальный размер для Уровня 1 |
| `RELAY_CHUNK_SIZE` | 512 байт | Базовый размер relay-пакета для расчёта N |
| `CONFIRM_MIN_N` | 2 | Минимальное N даже для мелких сообщений |
| `CREDIT_BASE` | 0 | Новый узел НЕ получает бесплатных кредитов |
| `CREDIT_LIMIT_FACTOR` | 20 × sqrt(reputation) | Лимит кредитной линии |
| `DUMMY_INTERVAL` | 60 сек | Как часто генерировать dummy-трафик при пустой очереди |

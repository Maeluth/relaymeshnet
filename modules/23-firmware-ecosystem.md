# Firmware Ecosystem

## Принцип

RMN — это протокол, не монолитная прошивка. Как Linux имеет одно ядро и сотни
дистрибутивов, так RMN имеет один протокол (wire format, onion routing, DHT,
tokenomics) и может иметь множество совместимых прошивок от разных разработчиков.

## Модель: прошивка как контент

Прошивка хранится в content-addressed storage (`04-content-storage.md`) и
распространяется через BitTorrent-подобный механизм. Популярные прошивки
автоматически реплицируются на большее число узлов.

```
Разработчик A (Maeluth):
  rmn-core v1.0 → SHA256 → 0xAAA... → chunk1...chunkN
  rmn-core v1.1 → SHA256 → 0xBBB... → chunk1...chunkN

Разработчик B (сторонний):
  rmn-custom v2.0 → SHA256 → 0xCCC... → chunk1...chunkN

DHT-запись: "firmware:dev_id/name/version" → {hash, signature, metadata}
```

## Подпись и верификация

```
Сборка прошивки:
  1. Компиляция → firmware.bin
  2. SHA256(firmware.bin) → FirmwareHash
  3. Ed25519_Sign(dev_privkey, FirmwareHash) → Signature
  4. Публикация в DHT: FirmwareRecord {hash, signature, version, metadata}

Установка:
  1. Скачать чанки через контент-слой
  2. Собрать firmware.bin
  3. Проверить SHA256(firmware.bin) == FirmwareHash
  4. Проверить Ed25519_Verify(dev_pubkey, Signature, FirmwareHash)
  5. Если обе проверки пройдены → применить
  6. Иначе → отвергнуть, пометить отправителя как malicious
```

## Совместимость

Любая прошивка, соблюдающая RMN Protocol (`17-protocol-spec.md`), совместима
с остальными. Capability negotiation (`18-versioning-compat.md`) позволяет
узлам с разными прошивками общаться:

```
Узел A (rmn-core v1.0, caps: [chat, relay, dht]):
  → HELLO → Узел B (rmn-custom v2.0, caps: [chat, relay, dht, web_host])

  A знает: B поддерживает web_host (может хостить сервисы)
  B знает: A не поддерживает web_host (не слать запросы на хостинг)

  Оба могут: обмениваться чатом, релеить, участвовать в DHT
```

## Экономика распространения

Узлы, хранящие и раздающие чанки прошивок, получают STORAGE_REWARD
(`05-tokenomics.md`). Популярные прошивки автоматически реплицируются:

```
rmn-core (150 узлов):
  → 150 провайдеров чанков
  → Скачивание быстрое (много источников)
  → Разработчик не платит за хостинг (сеть хранит)

rmn-lite (5 узлов):
  → 5 провайдеров
  → Скачивание медленнее
  → Разработчик может стимулировать хранение (заплатить STORAGE_REWARD)
```

## Обновление через mesh

```
1. Узел периодически проверяет DHT: есть ли новые версии установленной прошивки?
2. Если да:
   a) Скачивает FirmwareRecord (hash, signature)
   b) Скачивает чанки через контент-слой
   c) Проверяет подпись
   d) Применяет обновление (перезагрузка с новой прошивкой)
   e) Рассылает gossip: "я обновился до v1.1"
3. Соседи видят gossip → тоже проверяют → цепная реакция обновления
```

## Множественные разработчики

```
Разработчик = identity (Ed25519 keypair)
  → FirmwareID = SHA256(dev_pubkey + firmware_name)
  → Репутация разработчика в DHT определяет доверие

Новый разработчик:
  1. Генерирует ключи
  2. Собирает прошивку
  3. Подписывает
  4. Публикует в DHT

Пользователь выбирает прошивку по:
  - Репутации разработчика
  - Количеству узлов, уже использующих прошивку
  - Описанию и фичам
```

## Защита от зловредных прошивок

| Атака | Защита |
|---|---|
| Вирусная прошивка от имени Maeluth | Без приватного ключа — подпись не пройдёт |
| Подмена чанков при скачивании | SHA256 каждого чанка в манифесте |
| Разработчик-мошенник (низкая репутация) | UI показывает репутацию разработчика |
| Сговор разработчиков (fake reputation) | Weighted gossip (`16-crypto-identity.md`) — голоса новых узлов игнорируются |
| Прошивка-шпион (сливает данные) | Любая прошивка с открытым кодом может быть проаудирована сообществом |

## Параметры

| Параметр | Значение | Описание |
|---|---|---|
| `FIRMWARE_CHUNK_SIZE` | 256 KB | Размер чанка прошивки |
| `FIRMWARE_CHECK_INTERVAL` | 24 часа | Как часто проверять обновления |
| `FIRMWARE_MIN_SIGNERS` | 1 | Минимум подписей для принятия прошивки |
| `FIRMWARE_ROLLBACK_ENABLED` | true | Возможность отката к предыдущей версии |

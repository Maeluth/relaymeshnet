# Identity Export & Import 🟡 Required

> **Required.** Без механизма переноса identity пользователи теряют ключи, баланс и репутацию при смене устройства. Это не «удобство» — это необходимость для retention пользователей.

## Проблема

Пользователь меняет устройство (телефон, ноутбук) или переезжает в другую комнату
с новым роутером. Как перенести peerID, приватные ключи, баланс, репутацию и историю?

## Экспорт identity

```
WebUI → Settings → Export Identity → ввести парольную фразу

Создаётся зашифрованный бэкап-файл:
  identity.rmn — содержит:
    - Ed25519 private key (зашифрован парольной фразой)
    - Curve25519 private key (для X3DH)
    - PeerID
    - PoH seed + последний checkpoint
    - Баланс (подписанный снапшот)
    - Список контактов (peerID + pubkey)

Формат: JSON + AES-256-GCM, ключ = Argon2id(парольная фраза, соль)
```

### Структура бэкапа

```go
type IdentityBackup struct {
    Version       int
    PeerID        [16]byte
    Ed25519Priv   [32]byte  // зашифрован
    Curve25519Priv [32]byte // зашифрован
    PoHSeed       [32]byte
    PoHCheckpoint PoHCheckpoint
    BalanceProof  BalanceProof
    Contacts      []ContactEntry
    CreatedAt     uint64
}

type BalanceProof struct {
    Balance   float64
    Reputation float64
    PoHProof  []byte    // доказательство времени баланса
    Signature []byte    // подпись узла
}

type ContactEntry struct {
    PeerID   [16]byte
    PubKey   [32]byte
    Nickname string
    TrustLevel int  // 0-5
}
```

## Импорт identity

```
Новое устройство → WebUI → Import Identity → выбрать identity.rmn → ввести пароль

1. Расшифровать Ed25519 private key (Argon2id + AES-GCM)
2. Проверить: SHA256(Ed25519_pubkey)[:16] == PeerID
3. Сгенерировать новый Curve25519 keypair (если не в бэкапе)
4. Импортировать контакты
5. Предъявить BalanceProof соседям:
   → Соседи проверяют PoHProof (время)
   → Соседи проверяют gossip-репутацию
   → Если всё валидно → баланс и репутация восстановлены

6. Начать с RAMP-UP стадии (не SANDBOX — узел не новый, он доказал возраст)
```

## Cross-device sync (два устройства одновременно)

```
Сценарий: студент имеет телефон И ноутбук. Оба подключены к mesh.

Решение: одно устройство — primary (хранит identity), второе — secondary
(подключается к primary через WiFi, использует его баланс).

Телефон (primary):
  - Хранит приватные ключи
  - Имеет баланс и репутацию
  - Подписывает транзакции

Ноутбук (secondary):
  - Подключается к primary
  - Отправляет запросы на подпись
  - Не хранит приватные ключи
  - Баланс — общий с primary

Протокол:
  Secondary → Primary: "подпиши транзакцию X"
  Primary → пользователю: "подтвердить перевод 50 RELAY?"
  Пользователь подтверждает → Primary подписывает → транзакция уходит
```

## Физический перенос (флешка)

```
Самый надёжный способ — физический носитель:

1. Экспортировать identity.rmn на USB-флешку
2. Физически перенести флешку на новое устройство
3. Импортировать

Преимущества:
  - Не требует сети (новое устройство может быть офлайн)
  - Не требует доверия к промежуточным узлам
  - Флешка может быть зашифрована (LUKS/BitLocker)

Недостатки:
  - Требует физического доступа
  - Риск потери/кражи флешки (но без парольной фразы — бесполезно)
```

## Безопасность

| Риск | Защита |
|---|---|
| Кража identity.rmn | Зашифрован парольной фразой (Argon2id, высокая сложность подбора) |
| Подделка BalanceProof | Подписан приватным ключом + PoH-доказательство времени |
| Двойное использование identity | PoH age gate: нельзя использовать один identity на двух узлах одновременно |
| Потеря парольной фразы | Бэкап недоступен. Рекомендация: записать фразу на бумаге, хранить отдельно |
| Импорт на скомпрометированное устройство | Проверить устройство перед импортом. Использовать TEE/TrustZone если доступно |

## Параметры

| Параметр | Значение | Описание |
|---|---|---|
| `BACKUP_ENCRYPTION` | AES-256-GCM | Алгоритм шифрования бэкапа |
| `BACKUP_KDF` | Argon2id | Функция формирования ключа из пароля |
| `BACKUP_VERSION` | 1 | Версия формата бэкапа |
| `SYNC_TIMEOUT` | 30 сек | Таймаут запроса secondary → primary |

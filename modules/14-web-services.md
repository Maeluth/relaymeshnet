# L4/L5: Web Services & Browsing

## Задача

Дать пользователю опыт, близкий к обычному интернету: открыть «сайт» внутри mesh,
получить страницу, взаимодействовать с API. Не только чат — полноценные веб-сервисы.

## Что уже есть

| Компонент | Модуль | Роль в веб-сценарии |
|---|---|---|
| DHT + self-certifying имена | `03` | Найти сервис по имени, получить pubkey владельца |
| Onion routing | `02` | Анонимный транспорт запроса к серверу |
| Content-addressed storage | `04` | Кэширование статики (CSS, JS, картинки) на ближайших узлах |
| SDK для разработчиков | `09` | `RegisterService()`, `StoreContent()` |
| WebUI | simulation/ui | Интерфейс-браузер для каталога сервисов |

## Архитектура запроса

```
Пользователь (WebUI) → вводит "students-wiki" или кликает в каталоге
                           │
                    DHT.Get("students-wiki") → ServiceRecord {pubkey, TTL}
                           │
                    Onion.buildCircuit(owner, hops=3)
                           │
                    HTTP GET / → через onion-цепь → сервер сервиса
                           │
                    Ответ ← через onion-цепь ← сервер сервиса
                           │
                    WebUI рендерит страницу
```

## CDN-слой: статика vs динамика

```
Статические файлы (CSS, JS, изображения, шрифты, документы):
  → Хранятся в content-addressed storage (04)
  → ServiceRecord содержит маппинг: "/style.css" → ChunkHash 0xAAA
  → Ближайший узел, хранящий чанк, отдаёт файл напрямую (1 hop)
  → Задержка: LoRa SF7 ~0.5 сек, WiFi ~0.05 сек

Динамические запросы (API, формы, поиск):
  → Идут через onion-цепь к владельцу сервиса (3+ hop)
  → Задержка: WiFi 3 hop ~0.5 сек, LoRa SF7 3 hop ~2-3 сек
```

Это даёт гибридную производительность: статика — быстро (кеш рядом), динамика — медленнее (через onion), но приемлемо.

## Локальный HTTP-прокси

Каждый узел запускает локальный прокси на `127.0.0.1:8081`:

```
Браузер → http://students-wiki.mesh/ → прокси
  → DHT-поиск "students-wiki"
  → если статика: GET из контент-слоя (быстро)
  → если динамика: GET через onion (медленнее, но анонимно)
  → рендеринг в WebUI
```

Специальный TLD `.mesh` резолвится локально, без внешнего DNS.

## Маршрутизация запросов по типу контента

```
Запрос GET /api/search?q=lecture

1. Прокси определяет: /api/* → динамика
2. DHT.Get("students-wiki") → ServiceRecord
3. Onion.buildCircuit(owner, 3) → цепь
4. HTTP GET → цепь → сервер → ответ → прокси → WebUI

Запрос GET /style.css

1. Прокси определяет: .css → статика
2. ServiceRecord.files["/style.css"] → ChunkHash 0xBBB
3. DHT.GetProviders(0xBBB) → [peer1, peer2, peer3]  (кто хранит)
4. GET от ближайшего provider'а → 1 hop → быстро
```

## Время доставки: реалистичные оценки

| Сценарий | Hops | Канал | Время |
|---|---|---|---|
| Статика с соседнего узла | 1 | WiFi | ~0.05 сек |
| Статика с дальнего узла | 1 | LoRa SF7 | ~0.5 сек |
| Динамика через onion | 3 | WiFi | ~0.5 сек |
| Динамика через onion | 3 | LoRa SF7 | ~2-3 сек |
| Файл 50 KB через контент-слой | 1-3 | LoRa SF7 | ~5-10 сек |
| Файл 500 KB через контент-слой | 1-3 | LoRa SF7 | ~30-60 сек |

Не миллисекунды, но секунды. Для mesh без интернета — отлично.

## Разработка сервиса (SDK)

```go
func main() {
    node, _ := sdk.Connect(sdk.ModeHost)

    mux := http.NewServeMux()

    // Статика → кэшируется в контент-слое
    mux.Handle("/static/", sdk.StaticHandler("./public"))

    // Динамика → через onion
    mux.HandleFunc("/api/search", searchHandler)

    // Регистрируем в DHT
    node.RegisterService("students-wiki", mux, sdk.ServiceConfig{
        Public:   true,
        Replicas: 5,
    })

    select {} // держим сервер
}
```

## Отказоустойчивость через зеркалирование

Сервис не привязан к одному узлу:

1. Владелец публикует статику в контент-слой → автоматическая репликация
2. Любой узел-зеркало может отвечать на запросы к статике
3. Если владелец офлайн — статика всё ещё доступна
4. Динамика — только через владельца (нужен живой сервер)

Для полной отказоустойчивости динамики: либо несколько узлов-зеркал с реплицированной БД, либо stateless API + контент-слой как backing store.

## Приоритеты и QoS

```
Тип трафика → Приоритет:
  1. Интерактивный (чат, API-запросы)     — высокий
  2. Статика (CSS, JS, страницы)          — средний
  3. Файлы, документы                     — низкий
  4. Dummy-трафик, gossip                 — фоновый
```

Пользовательский опыт: чат отвечает мгновенно, страницы грузятся за секунды, файлы — с индикатором прогресса.

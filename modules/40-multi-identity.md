# Multi-Identity Protocol 🟢 Optional

> **Optional.** Позволяет одному устройству держать несколько identity одновременно. Решает сценарии теневого бойкота, принудительного суверенитета и сброса репутации. Не обязателен для работы сети, но критичен для свободы пользователя.

## Мотивация

### Сценарий 1: Теневой бойкот (теневая монополия)

```
Картель из 30% узлов вносит жертву в локальные чёрные списки.
Жертва теряет relay-трафик, не может отправлять сообщения.
→ Создать новый PeerID = потерять всю репутацию и credit limit.
→ С Multi-Identity: создать второй ID на том же устройстве без потери первого.
```

### Сценарий 2: Принудительный суверенитет

```
Администрация зоны требует: «при подключении — регистрируйся в суверенитете».
Без Multi-Identity: один ID = раскрытие личности.
С Multi-Identity: ID_публичный в суверенитете + ID_скрытый анонимный.
```

### Сценарий 3: Career Progression Reset

```
TRUSTED-узел (90+ дней, reputation 50+), PeerID скомпрометирован.
Без Multi-Identity: удалить PeerID = потерять 90 дней репутации.
С Multi-Identity: старый ID продолжает работать, новый ID растёт параллельно.
```

## Принцип

Multi-Identity — это **не «кошелёк с несколькими аккаунтами»**.
Это ресурсно-ограниченная функция HAL:

```
┌─────────────────────────────────────────────────┐
│                 ФИЗИЧЕСКОЕ УСТРОЙСТВО              │
│                                                  │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐          │
│  │ ID_1    │  │ ID_2    │  │ ID_3    │  ...     │
│  │ primary │  │ hidden  │  │ backup  │          │
│  │ (public)│  │ (passwd)│  │ (fresh) │          │
│  └────┬────┘  └────┬────┘  └────┬────┘          │
│       │            │            │                │
│       └────────────┼────────────┘                │
│                    │                             │
│   ┌────────────────┴────────────────┐            │
│   │         ОБЩИЕ РЕСУРСЫ            │            │
│   │  • SX1276 (duty cycle 1%)       │            │
│   │  • CPU ядра                      │            │
│   │  • RAM                           │            │
│   │  • Flash / Storage               │            │

│   └─────────────────────────────────┘            │
└─────────────────────────────────────────────────┘
```

## Лимиты

Количество identity на одном устройстве ограничено **физическими** ресурсами,
не социальными:

```go
func MaxIdentities(device *HALInfo) int {
    ramLimit     := device.RAM_MB / 128          // 256 MB → 2, 512 MB → 4
    cpuLimit     := int(float64(device.CPU_Cores) * 1.5)  // 2 ядра → 3, 4 ядра → 6
    dutyLimit    := int(1.0 / 0.003)             // 0.3% duty cycle на ID → 3
    storageLimit := device.Flash_MB / 32          // 32 MB Flash на ID
    
    return min(ramLimit, cpuLimit, dutyLimit, storageLimit)
}
```

| Устройство | RAM | CPU | Flash | Max ID |
|---|---|---|---|---|
| ESP32 (минимальный) | 520 KB | 2 ядра | 4 MB | 1 |
| Raspberry Pi Zero 2W | 512 MB | 4 ядра | SD card | 3-4 |
| OpenWRT роутер (128MB) | 128 MB | 1 ядро | 16 MB | 1 |
| OpenWRT роутер (256MB) | 256 MB | 2 ядра | 32 MB | 2 |
| OpenWRT роутер (512MB) | 512 MB | 4 ядра | 128 MB | 4 |
| Mini-PC / сервер | 4096 MB | 8 ядер | SSD | 6 |

Ограничение: ESP32+SX1276 (базовый relay-узел) **НЕ** поддерживает Multi-Identity — RAM
хватает только на одну identity с минимальной функциональностью.

## Санкционирование

Каждый ID на одном устройстве проходит независимый SANDBOX:

```
ID_1 (создан первым):
  → SANDBOX (7 дней) → RAMP-UP (30 дней) → ACTIVE → TRUSTED

ID_2 (создан через 3 дня после ID_1):
  → SANDBOX (7 дней с момента создания) → RAMP-UP → ...

ID_3 (создан через 30 дней после ID_1):
  → SANDBOX (7 дней) → RAMP-UP → ...

Каждый ID:
  - Свой приватный ключ (Ed25519)
  - Свой PeerID = SHA256(pubkey)[:16]
  - Своя репутация (EWMAWork, PoH-возраст)
  - Свой баланс RELAY
  - Свои trust-списки, бан-листы
  - Свой onion-профиль
```

**Правила:**
- ID'ы одного устройства НЕ знают друг о друге на уровне протокола
- ID'ы одного устройства НЕ могут прямо обмениваться RELAY (запрещено PoR-проверкой: одна антенна = self-mining)
- Балансы разделены — трансфер между ID'ами возможен только через третьего relay
- Gossip-записи для разных ID разделены
- DHT-записи не пересекаются (разные XOR-зоны, разные ключи)

## Экономика: почему это не эксплойт

### Суммарный заработок

```
Одиночный ID на роутере (256 MB RAM):
  - Relay: 100% duty cycle доступно (до 1%)
  - CPU: 100% на один onion-поток
  - RAM: 100% на один DHT-сегмент
  → Базовый доход: X RELAY/день

2 ID на том же роутере:
  - Relay: ~50% duty cycle каждому (0.5% из 1%)
  - CPU: ~50% каждому (contention при одновременной onion-расшифровке)
  - RAM: ~50% каждому (128 MB на ID, меньше DHT-записей)
  - Но: 2 ID в relay-выборе вместо 1 → шанс быть выбранным выше
  
  ID_1 доход: ~0.55-0.75 X (потеря от contention, выигрыш от статистики)
  ID_2 доход: ~0.55-0.75 X (SANDBOX — меньше, но растёт)
  Суммарно:   ~1.1-1.5 X

3 ID:
  Суммарно: ~1.0-1.3 X (contention перевешивает статистический выигрыш)
  
4+ ID:
  Суммарно: ~0.8-1.0 X (убыток от contention)
```

Вывод: **максимальный выигрыш — 2-3 ID на мощном устройстве.**
4+ ID уже убыточны. Физика не обманывается.

### Почему Sybil-атакер не может создать 100 ID

```
Атакер на VPS (64 ядра, 128 GB RAM):
  → MaxIdentities() = min(131072/128, 64*1.5, 3) = 3
  → Ограничение по duty cycle: 3 ID максимум

Если атакер ПОДДЕЛЫВАЕТ HAL-отчёт:
  → Соседи видят что device声称 64 ядра но реальный throughput = 2 ядра
  → Gossip разносит anomaly flag
  → Reputation demurrage ×4 за ложный HAL-отчёт

Если атакер использует 100 физических ESP32:
  → 100 × $5-15 = $500-1500 за железо
  → 100 × 7 дней SANDBOX = ресурс времени
  → Суммарный доход: 100 × ~0.1 X = ~10 X
  → Окупаемость: годы при малом количестве узлов в сети
```

## Correlation-защита (Anti-Discovery)

Несколько ID на одном устройстве — это корреляционная мишень.
Противник может сопоставить:

- Радио-сигнатуры (одинаковая антенна, одинаковый RSSI-паттерн для соседей)
- Физическое местоположение (один и тот же набор соседей)
- Время появления/исчезновения (перезагрузка роутера роняет все ID)
- Паттерны активности (коррелированные всплески CPU-нагрузки)

### Протокол десинхронизации

```go
type IdentityDesync struct {
    // Случайная задержка старта второго ID
    StartDelayMin  time.Duration // 0 минут
    StartDelayMax  time.Duration // 60 минут
    
    // Разные параметры cover traffic для каждого ID
    CoverLambdaMin float64 // 0.5 сообщений/сек
    CoverLambdaMax float64 // 2.0 сообщений/сек
    
    // Разное расписание relay-активности
    ActiveHours []int // часы активности ID (разные для разных ID)
    
    // Разные onion-профили
    OnionProfile string // "light", "medium", "full" — разные для разных ID
}

func (d *IdentityDesync) ScheduleForID(idIndex int) Schedule {
    rng := rand.New(rand.NewSource(time.Now().UnixNano() + int64(idIndex*1000000)))
    
    // Стартовая задержка
    startDelay := d.StartDelayMin + time.Duration(rng.Int63n(int64(d.StartDelayMax)))
    
    // Cover traffic lambda
    lambda := d.CoverLambdaMin + rng.Float64()*(d.CoverLambdaMax-d.CoverLambdaMin)
    
    // Часы активности
    // ID_1 активен 06:00-02:00, ID_2 активен 08:00-04:00
    shift := (idIndex * 3) % 24
    activeHours := make([]int, 0)
    for h := shift; h < shift+20; h++ {
        activeHours = append(activeHours, h%24)
    }
    
    return Schedule{
        StartDelay:   startDelay,
        CoverLambda:  lambda,
        ActiveHours:  activeHours,
        OnionProfile: onionProfileForIndex(idIndex),
    }
}
```

### Что это даёт

| Параметр | ID_1 | ID_2 | Эффект |
|---|---|---|---|
| Старт | t=0 | t=17 мин | Корреляция старта размыта |
| Cover λ | 0.8 msg/s | 1.5 msg/s | Разные паттерны трафика |
| Активные часы | 06-02 | 08-04 | Частичное пересечение, но не полное |
| Onion | medium | light | Разная глубина hop'ов |

Противник всё ещё МОЖЕТ коррелировать — но цена анализа растёт экспоненциально
от числа ID. Для 2 ID на одном устройстве при хорошей десинхронизации:
- Ложное срабатывание (FP): ~30% (принял разные устройства за одно)
- Ложный пропуск (FN): ~40% (не заметил что ID_1 и ID_2 = один человек)
- Точность: недостаточна для уверенного вывода

## Скрытые identity (Stealth Mode)

```
ID_1: публичный, виден в списке identity устройства
ID_2: скрыт за паролем, не отображается в UI без ввода пароля

WebUI → Настройки → Identity:
  ┌─────────────────────────────────────────────┐
  │  Активные identity                           │
  │                                              │
  │  ID_1 (public)  ████████░░  ACTIVE  87 дней │
  │  ID_2 (hidden)  ████░░░░░░  RAMP-UP 12 дней │
  │                                              │
  │  [Создать новый ID]                          │
  │  [Показать скрытый ID]  ← требует пароль     │
  └─────────────────────────────────────────────┘

Без пароля:
  устройство для внешнего наблюдателя = "один ID, зарегистрирован в суверенитете"
  ID_2 не существует для проверяющего
```

**Реализация:**
- ID_2 хранится зашифрованным (AES-256-GCM, ключ = Argon2id(пароль))
- Без расшифровки ID_2 не подписывает пакеты, не релеит, не отвечает на ping
- ID_2 «просыпается» только при вводе пароля
- После таймаута бездействия (30 минут) — снова шифруется и «засыпает»

Это не «скрытый раздел диска». Это криптографически защищённая identity.

## Переключение identity для relay-выбора

Устройство с несколькими ID представляет их в relay-выбор **раздельно**:

```
Relay-запрос: «кто может relay 512 байт?»

Устройство A (3 ID):
  - ID_1: reputation 45.2, weight = 45.2 × 0.7 + clan×0.3 = 38.1
  - ID_2: reputation 12.7, weight = 12.7 × 0.7 + 0×0.3 = 8.9
  - ID_3: reputation 0.5,  weight = 0.5  × 0.7 + 0×0.3 = 0.35

  → В relay-выбор попадают как три независимых кандидата
  → Но физически: одно устройство, один duty cycle
  → Если ID_1 уже выбран для relay — ID_2 и ID_3 НЕ могут релеить одновременно
    (duty cycle занят)
```

Правило: **один relay в один момент времени на устройство, независимо от числа ID.**
Выбирается ID с наивысшей репутацией.

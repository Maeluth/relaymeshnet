# Pending Queue 🟡 Required

> **Required.** Без pending-очереди офлайн-транзакции теряются. В mesh с частыми разрывами связи это критично: переводы, файлы, сообщения — всё должно ждать получателя.

## Принцип

Баланс привязан к физическому узлу. Отправить можно только тому, кого видишь.
Не видишь → транзакция уходит в pending queue на узле отправителя и ждёт
восстановления связи.

## Правила

| Правило | Описание |
|---|---|
| **0** | Баланс существует на конкретном узле. Нет связи с узлом = нет доступа к балансу |
| **1** | Отправить можно только достижимому получателю. Недостижим → pending |
| **2** | Сумма pending блокируется на балансе отправителя (`locked_out`) |
| **3** | Pending НЕ увеличивает баланс получателя до фактического завершения |
| **4** | Обработка FIFO: старые pending выполняются первыми |
| **5** | Если при завершении баланс изменился и средств не хватает → отмена |

## Модель баланса

```
balance       = фактический баланс узла
locked_out    = сумма всех исходящих pending
available     = balance - locked_out (сколько можно потратить прямо сейчас)
```

## Жизненный цикл транзакции

```
Создание:
  if amount > available → ❌ отказ
  locked_out += amount
  добавить в pending_out (FIFO)

Ожидание (retry каждые 5 минут):
  if now - created_at > TTL (24ч) → expire:
    locked_out -= amount
    уведомить отправителя: "TTL истёк, средства возвращены"

  if receiver достижим:
    if amount <= balance:
      → complete:
        balance -= amount
        locked_out -= amount
        уведомить обе стороны
    else:
      → cancel (баланс изменился, обещание невыполнимо):
        locked_out -= amount
        уведомить отправителя: "недостаточно средств"

Отмена вручную (отправителем):
  locked_out -= amount
  статус = cancelled
```

## Примеры

### Базовый сценарий

```
Алиса: balance=100, locked_out=0, available=100

TX1 → Боб (50, pending): locked_out=50, available=50
TX2 → Чарли (30, pending): locked_out=80, available=20
TX3 → Дана (25): available(20) < 25 → ❌ отказ

Боб появился:
  TX1 complete: balance=50, locked_out=30, available=20

Чарли появился:
  TX2 complete: balance=20, locked_out=0, available=20
```

### Отправитель потратил средства между созданием pending и завершением

```
Алиса: balance=100

TX1 → Боб (50, pending): locked_out=50, available=50
TX2 → Чарли (40, pending): locked_out=90, available=10

Алиса отправила 80 Дане (онлайн):
  balance = 100 - 80 = 20
  available = 20 - 90 = -70

Боб появился:
  TX1: 50 <= balance(20)? → ❌ НЕ ХВАТАЕТ
  TX1 cancelled: locked_out = 90 - 50 = 40

Чарли появился:
  TX2: 40 <= balance(20)? → ❌ НЕ ХВАТАЕТ
  TX2 cancelled: locked_out = 0
  available = 20
```

Оба pending отменились — отправитель потратил заблокированные средства.
Получатели не пострадали (они не знали о pending).

### FIFO защита

```
TX1 → Боб (50, pending) — создана 10:00
TX2 → Чарли (50, pending) — создана 10:05

Боб и Чарли появились одновременно в 11:00.
Обработка ТОЛЬКО в порядке создания: TX1 первая, TX2 вторая.
Нельзя выполнить TX2 раньше TX1, даже если Боб и Чарли оба доступны.
Это защищает Боба: его более старое обещание не может быть нарушено в пользу Чарли.
```

### Входящий pending не виден получателю

```
Алиса → Боб (50, pending)
Баланс Боба: 200 (не изменился!)

Боб НЕ МОЖЕТ потратить эти 50:
  - Он не знает о pending входящем
  - Его баланс не учитывает pending incoming

Только когда транзакция completed → баланс Боба становится 250.
Это предотвращает каскадные зависимости.
```

## Bridge и внешние сообщения

Bridge использует два механизма доставки в зависимости от ситуации:

```
1. DHT Mailbox (07-bridge-external.md) — PULL, основной:
   Bridge кладёт зашифрованное сообщение в DHT по ключу mailbox_key.
   Получатель polling'ом забирает, когда онлайн.
   Работает даже если получатель был офлайн в момент получения bridge'ом.
   Сообщение живёт в DHT с TTL = TTL_mailbox (обычно 24 часа).

2. External Pending Queue — PUSH, для urgent/гарантированной доставки:
   Bridge пытается активно доставить сообщение получателю.
   Подходит для срочных сообщений или когда отправитель хочет знать
   точный статус доставки.
```

### Когда какой механизм

| Ситуация | Механизм |
|---|---|
| Получатель онлайн, DHT достижим | DHT Mailbox (быстрее) |
| Получатель офлайн | DHT Mailbox (он заберёт когда появится) |
| Отправитель хочет tracking/подтверждение | External Pending (есть статусы) |
| Срочное сообщение | External Pending (активная доставка) |
| DHT-разделён (partition), получатель в другой подсети | External Pending (ждём воссоединения) |

### External Pending Queue (Bridge)

```
Внешний отправитель → Bridge API → mesh узел (недоступен)

Bridge создаёт ExternalPending в своей очереди:
  - Внешний отправитель получает tracking ID
  - Может запрашивать статус: GET /api/delivery/{tracking_id}
  
Статусы:
  "queued"     — в очереди, получатель недоступен
  "delivered"  — доставлено (confirmed)
  "expired"    — TTL истёк, получатель не появился
  "failed"     — ошибка доставки

Параметры:
  TTL: 24 часа (по умолчанию)
  Retry: каждые 5 минут
```

## Почему TTL измеряется wall-clock, а не PoH

TTL в pending queue — локальный таймаут на узле отправителя. Измеряется по
системным часам (`time.Now()`), а не PoH-тиками. Причины:

1. PoH-тики разных узлов не синхронизированы. 1000 тиков на узле А ≠ 1000 тиков на узле Б.
2. TTL не требует проверки другими узлами — это локальное решение отправителя.
3. PoH нужен для меж-узловых доказательств (PoR, reputation), а не для локальных таймаутов.

**Риск**: злонамеренный узел может перевести системные часы назад и продлить TTL.
**Защита**: замороженный узел (баланс < -100) всё равно не может отправлять.
Продление TTL даёт мошеннику только отсрочку возврата средств — но средства
всё ещё заблокированы, он не может их использовать.

| Параметр | Значение | Описание |
|---|---|---|
| TTL | 24 часа | Время жизни pending транзакции |
| Retry interval | 5 минут | Как часто проверять доступность получателя |
| Max pending per sender | 50 | Максимум одновременных pending |
| Reachability check timeout | 10 секунд | Таймаут пинга при проверке |

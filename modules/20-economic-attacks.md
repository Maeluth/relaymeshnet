# Economic Attack Vectors 🟡 Required

> **Required.** Без защиты от self-mining, Sybil-reset и cross-network migration экономика уязвима. PoH age gate и reputation ramp-up — не опции, а необходимость.

## 1. Sybil Reset Attack (сброс устройства для создания кредитов)

### Механика

```
Атакующий:
  1. Узел релеит трафик → зарабатывает +100 RELAY
  2. Переводит 100 RELAY на второй узел (свой)
  3. Сбрасывает первый узел до заводских настроек
  4. Первый узел получает новый identity → баланс 0
  5. Старый долг "исчез" (никто не знает что это тот же узел)
  6. 100 RELAY остались у второго узла
  7. Повторить ×100 → 10000 RELAY создано из ничего
```

### Защита: PoH Age Gate + Reputation Ramp-Up

```
День 0-7 (Sandbox):
  - Эмиссия confirm-N: заблокирована в escrow (накапливается, но недоступна)
  - Relay-вознаграждение: ×0.1 от нормального
  - Не может отправлять файлы > 10 KB
  - Не может переводить RELAY другим узлам
  - Credit limit = 0 (не может уйти в минус)
  - Не выбирается в onion-цепи как relay (только confirm-N)

День 7-30 (Ramp-up):
  - Escrow разблокируется
  - Relay-вознаграждение: ×1.0
  - Credit limit = 20 × sqrt(reputation)
  - Может переводить RELAY (до credit_limit)
  - Выбирается в onion-цепи (reputation-weighted)

День 30+ (Full):
  - Все возможности без ограничений
```

**Экономический анализ атаки:**
- 7 дней Sandbox × 0.1 вознаграждения = копейки
- Сброс → снова 7 дней Sandbox
- За месяц атакующий может сделать 4 цикла сброса
- Доход: 4 × 7 дней × 0.1 × средний_relay_объём ≈ ничтожно
- Вывод: атака экономически бессмысленна

## 2. Cross-Network Credit Migration

### Механика

```
Узел из сети А (накопил 1000 RELAY, reputation 50) приходит в сеть Б.
Сеть Б не знает этот узел. Если принять его reputation как есть:
  → Узел получает несправедливое преимущество в новой сети
  → Может доминировать в relay-выборе
```

### Защита: Cross-Network Reputation Verification

```
При обнаружении узла из другой сети (peerID не в локальном DHT):

1. Запросить PoH-доказательство возраста:
   - Если возраст < 7 дней → Sandbox (возможно, Sybil)
   - Если возраст > 7 дней → проверить cross-references

2. Запросить cross-references у соседей:
   - Нужно 3+ подписи от известных узлов из сети А
   - Подписи подтверждают: "peerID X имеет reputation Y на момент tick Z"
   - Проверить PoH цепочки подписавших узлов

3. Начать локальный ramp-up в сети Б:
   - Первые 7 дней: reputation = 0 (локально)
   - Relay-выбор: weight = 0 (не выбирается)
   - Баланс: сохраняется (заработан честно)
   - После 7 дней локальной работы: reputation растёт

4. Слияние reputation:
   - После 30 дней в сети Б:
     merged_reputation = (local_rep × 0.7 + imported_rep × 0.3)
   - Местная работа весит больше чем импортированная
```

## 3. Self-Mining (Fake Relay)

### Механика

```
Атакующий контролирует два узла A и B в одной сети.
A «отправляет» 1 ГБ данных B через onion-цепь.
Оба получают PoR квитанции за «relay».
→ 1 ГБ × 2 × RELAY_REWARD = нечестный доход
```

### Защита: Multi-Hop PoR + Anomaly Detection

```
1. PoR требует подписи СЛЕДУЮЩЕГО hop'а в onion-цепи.
   Нельзя подписать самому себе.
   Для self-mining нужно контролировать минимум 3 узла в цепи.

2. Sybil-защита (S/Kademlia PoW puzzle):
   Создать 3 узла с валидными NodeID — вычислительно затратно.

3. Anomaly detection (gossip):
   Если пара узлов A-B обменивается трафиком в 1000× больше
   чем с остальной сетью → anomaly flag → reputation penalty.

4. PoH cross-reference:
   "Я релеил A→B в tick_X" — но соседи видят что в tick_X
   узлы A и B были в одном месте (WiFi RSSI) → подозрительно.
```

## 4. Self-Mining через Confirm-N

### Механика

```
Атакующий генерирует фальшивый трафик:
  1. Узел A → confirm-2 (релеит 2 чужих пакета)
  2. Но «чужие» пакеты созданы тем же узлом A через второй identity
  3. Эмиссия начисляется за фальшивую работу
```

### Защита

```
1. Relay-очередь принимает пакеты ТОЛЬКО от разных peerID.
   Нельзя релеить пакет, созданный тем же узлом (по IP/MAC/radio fingerprint).

2. Confirm-N эмиссия ограничена сверху:
   max_daily_emission = EMISSION_RATE × MAX_DAILY_CONFIRM_KB
   MAX_DAILY_CONFIRM_KB = 10 MB/день

3. Аномалия: если confirm-N одного узла > 10× среднего по сети → флаг.
```

## 5. Параметры защиты

| Параметр | Значение | Описание |
|---|---|---|
| `SANDBOX_DURATION` | 7 дней | Новый узел ограничен |
| `RAMPUP_DURATION` | 30 дней | Постепенное снятие ограничений |
| `SANDBOX_REWARD_MULT` | 0.1 | Множитель relay-вознаграждения в sandbox |
| `MIN_CROSS_REFS` | 3 | Минимум подтверждений для cross-network узла |
| `LOCAL_REP_WEIGHT` | 0.7 | Вес локальной репутации при слиянии сетей |
| `MAX_DAILY_CONFIRM_KB` | 10 MB | Максимум confirm-N трафика в день |

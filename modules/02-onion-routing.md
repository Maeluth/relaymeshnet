# L2: Onion Routing 🔴 Core

> **Core.** Без onion-маршрутизации нет анонимности. Relay-логика, построение цепей, cover traffic — это протокол.

## Принцип

Onion routing обеспечивает анонимность отправителя и получателя в mesh-сети.
Аналогичен Tor, но адаптирован под unreliable mesh без интернета.

Каждое сообщение проходит через цепь из N узлов (по умолчанию N=3). Каждый узел
знает только предыдущий и следующий hop, но не знает полный путь.

## Наслоение шифрования

```
Сообщение для D
  → зашифровано ECDH(D_pub, S_priv)
    → обёртка: "next = D"
      → зашифровано ECDH(N3_pub, S_priv)
        → обёртка: "next = N3"
          → зашифровано ECDH(N2_pub, S_priv)
            → обёртка: "next = N2"
              → зашифровано ECDH(N1_pub, S_priv)
                → обёртка: "next = N1"
```

NaCl `box.Seal`/`box.Open` (Curve25519 + XSalsa20-Poly1305) — основа шифрования.
Достаточно обернуть рекурсивно (см. `17-protocol-spec.md` раздел 3).

## Структура onion-пакета и размеры

```go
type OnionPacket struct {
    Version   byte
    HopData   []byte   // зашифровано для текущего hop
    Payload   []byte   // вложенный onion-пакет или финальное сообщение
}
```

Каждый HopData содержит (после расшифровки):
- `NextHop`: peerID следующего узла (32 байта — SHA256) или nil (1 байт)
- `InnerPayload`: зашифрованный вложенный пакет

**Размер onion-пакета (3 hop'а, NaCl box overhead 40 байт/слой)**:

```
Onion_size = M + 185 байт (где M — размер исходного сообщения)

┌──────────────────────────────────────────────┐
│ LoRa-фрейм (до 222 байт для SF7)             │
│ ┌──────────────────────────────────────────┐ │
│ │ Onion-пакет (M + 185 байт)               │ │
│ │ ┌──────┬──────────────────────────────┐  │ │
│ │ │ Верс │ HopData (зашифрован для hop1)│  │ │
│ │ │ 1B   │ M + 184 байта                │  │ │
│ │ └──────┴──────────────────────────────┘  │ │
│ └──────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

| Исходное сообщение M | Onion-пакет | Влезает в SF7 (222B)? | Влезает в SF12 (51B)? |
|---|---|---|---|
| 20 B ("Hi") | 205 B | Да (1 фрейм) | Нет (5 фрагментов) |
| 200 B (~3 строки) | 385 B | Нет (2 фрагмента) | Нет (8 фрагментов) |
| 1024 B | 1209 B | Нет (6 фрагментов) | Нет (24 фрагмента) |

### Фрагментация на транспортном уровне

Транспортный слой (`01-transport-layer.md`) автоматически фрагментирует пакеты,
превышающие MTU канала, и собирает на стороне получателя. Onion-слой не знает
о фрагментации.

**Влияние на latency (SF7, 5.5 кбит/с, 1% duty cycle)**:

| Onion-пакет | Фрагментов | Время передачи (эфир) | Время с duty cycle |
|---|---|---|---|
| 205 B | 1 | 0.05 с | 5 с |
| 385 B | 2 | 0.11 с | 11 с |
| 1209 B | 6 | 0.33 с | 33 с |

### Onion-Lite для SF12 (только контрольные сообщения)

Для SF12 (51 байт/фрейм, экстремальная экономия) используется onion-lite:
- Только 1 hop вместо 3 (меньше анонимность, но хоть что-то)
- Пакет: M + 65 байт (1 слой вместо 3)
- При M=20: 85 байт → 2 фрагмента SF12
- Только для ping'ов, ACK, keepalive

## Построение цепи

```go
type CircuitBuilder struct {
    dht   *DHT
    peers []PeerInfo
}

func (cb *CircuitBuilder) BuildCircuit(target PeerID, hops int) (*Circuit, error) {
    // 1. Запросить DHT: топ-100 узлов по reputation
    candidates := cb.dht.QueryReputation(100)

    // 2. Исключить target и себя
    candidates = filter(candidates, cb.myID, target)

    // 3. Выбрать N случайных из топа (ротация для безопасности)
    selected := randomSubset(candidates, hops)

    // 4. Построить onion-пакет рекурсивно
    packet := buildOnion(target, selected, payload)

    return &Circuit{Hops: selected, Packet: packet}, nil
}
```

## Pool пребилженных цепей

В unreliable mesh (LoRa) нельзя ждать построения цепи для каждого сообщения.
Решение: узел постоянно держит пул из K готовых цепей.

### Адаптация под физику канала

LoRa имеет жёсткие ограничения duty cycle (1% в EU, означает что на 1 секунду
эфирного времени требуется ~100 секунд ожидания). Полноценный circuit pool
на чистом LoRa нереализуем. Стратегия зависит от доступных каналов:

| Канал | K (цепи) | Ping | Ротация | Обоснование |
|---|---|---|---|---|
| **WiFi** | 5 | 2 с | 10 мин | Полноценный пул |
| **WiFi + LoRa** | 3 WiFi / 1 LoRa | WiFi: 2 с, LoRa: 120 с | 10 мин | LoRa-цепь как fallback |
| **Только LoRa** | 1 | 120 с | 30 мин | Минимальный пул, цепь строится lazy |

На чистом LoRa (SF12, 0.3 кбит/с) пинг 50 байт через 3 hop'а требует:
- 50 байт пакет, 3 hop'а = 150 байт × 8 / 300 бит/с = 4 секунды передачи
- При duty cycle 1%: 4 × 100 = 400 секунд (~7 минут) на один ping
- Одна цепь с ротацией каждые 30 минут = 2 ping'а в час = ~14 минут эфирного времени
- При 1% duty cycle это 1400 секунд ожидания из 3600 → приемлемо

### Алгоритм (адаптивный)

```
Фоновый процесс (каждые 60 секунд):
  Для каждого активного канала:
    Если в пуле < K_канала цепей:
      Построить новую цепь, отправить ping (размер 50 байт)
      Если ACK → добавить в пул как "живую"
      Если timeout → отбросить
    Ротировать цепи старше TTL_канала

Отправка сообщения:
  Выбрать цепь из пула, приоритет WiFi > LoRa
  Отправить
  При неудаче → fallback на другую цепь (включая LoRa-fallback цепь)
  Если все готовые цепи отказали → построить цепь lazy (on-demand)
```

### Lazy circuit building (fallback для LoRa)

Если готовых цепей нет, а отправить нужно СЕЙЧАС:
- Для текстового сообщения: построить цепь on-demand
- Для файла: разбить на чанки, первые чанки пустить через lazy-цепь,
  параллельно строить pool цепи для остальных

### Параметры

| Канал | K | Ping таймаут | Ротация |
|---|---|---|---|
| WiFi | 5 | 2 с | 10 мин |
| LoRa SF7 | 3 | 15 с | 15 мин |
| LoRa SF12 | 1 | 120 с | 30 мин |

## Source routing с fallback

При обрыве цепи используется запасной маршрут:

```
Цепь: [S] → [N1] → [N2] → [N3] → [D]
           ↓ fail
         [N1'] → [N2] → [N3] → [D]   (перестроена на лету)
```

Каждый hop в onion-пакете может содержать список fallback-узлов.
Если основной следующий hop недоступен — пробуем fallback из того же
географического кластера.

## Relay-логика на каждом узле

```go
func (n *Node) HandleOnionPacket(packet []byte) {
    // 1. Попытаться расшифровать своим приватным ключом
    hopData, inner, err := crypto.UnwrapLayer(n.keyPair.PrivateKey, packet)
    if err != nil {
        // Не нам — игнорируем (или релеим как непрозрачный relay)
        n.relayBlindly(packet)
        return
    }

    // 2. Мы — один из hop'ов в цепи
    if hopData.NextHop == nil {
        // Мы — финальный получатель
        // inner содержит исходное сообщение
        n.handleIncomingMessage(inner)
        return
    }

    // 3. Мы — промежуточный hop
    // inner содержит вложенный onion-пакет
    n.transport.Send(hopData.NextHop, inner, PriorityRelay)

    // 4. Записать PoR (Proof of Relay)
    n.recordRelayProof(packet)
}
```

## Мультиканальность: striping через параллельные цепи

Файлы и большие сообщения разбиваются на чанки и идут через разные цепи:

```
Файл → chunk1, chunk2, chunk3
  chunk1 → цепь [S]→[A]→[B]→[D]
  chunk2 → цепь [S]→[C]→[E]→[D]   (параллельно)
  chunk3 → цепь [S]→[F]→[G]→[D]   (параллельно)
```

- ×N пропускная способность (N = количество параллельных цепей)
- Повышенная отказоустойчивость (потеря одной цепи ≠ потеря сообщения)
- Повышенная анонимность (разные части идут разными путями)

С erasure coding (см. `04-content-storage.md`) требуется только K из M чанков
для восстановления, так что потеря части цепей не критична.

## Защита от корреляции: Cover Traffic (Nym-модель)

В отличие от Tor, где cover traffic опционален, RelayMeshNet делает его **обязательным**.
Без константного потока трафика анонимность — иллюзия: даже пассивный наблюдатель
выделяет активных пользователей по наличию трафика.

### Принцип

```
Каждый узел передаёт с ПОСТОЯННОЙ скоростью (Poisson process):

  - Интервалы между передачами: экспоненциальное распределение со средним λ
  - Есть реальные данные → заменяют cover-пакет в ближайшем слоте
  - Нет реальных данных → loop-пакет (возвращается к отправителю)
  
  Loop-пакеты:
    - Зашифрованы так же, как реальные (Sphinx-подобный формат)
    - Проходят полный onion-путь и возвращаются к отправителю
    - Служат liveness check: если loop не вернулся → что-то не так с цепью
    - Нарушитель НЕ МОЖЕТ отличить loop от реального пакета
```

### Параметры потока

```
Базовый поток:     1 пакет/сек (высокая анонимность)
Экономный поток:   1 пакет/10 сек (приемлемая анонимность, меньше трафика)
Минимальный:       1 пакет/60 сек (базовая маскировка, низкие затраты)

Узел выбирает уровень в зависимости от баланса:
  Баланс > 100:    базовый поток (1/сек)
  Баланс 0-100:    экономный (1/10 сек)
  Баланс < 0:      минимальный (1/60 сек)
```

### Экспоненциальные задержки (Nym)

Uniform jitter (50-500ms) даёт минимальную энтропию тайминга.
Экспоненциальное распределение — максимальную.

```go
// Было:
jitter := time.Duration(50+rand.Intn(450)) * time.Millisecond

// Стало (Exponential distribution):
// X = -ln(U) / λ, где U ~ Uniform(0,1), λ = 1/mean
jitter := time.Duration(-math.Log(rand.Float64()) * float64(meanDelay))
```

| Параметр | Было (Uniform) | Стало (Exponential) |
|---|---|---|
| Распределение | Uniform(50ms, 500ms) | Exponential(mean=250ms) |
| Энтропия тайминга | Низкая | **Максимальная** |
| Максимальная задержка | 500ms | Не ограничена (хвост) |
| Предсказуемость | Высокая | **Низкая** |

### Почему это важно

```
Uniform jitter:
  Наблюдатель знает: "задержка всегда между 50 и 500ms"
  → Может оценить расстояние/hop'ы по задержке

Exponential jitter:
  Наблюдатель знает: "задержка ~250ms в среднем, но может быть и 2 секунды"
  → Не может оценить расстояние/hop'ы
  → Не может отличить relay-задержку от намеренной задержки
```

## Сравнение с Tor

| | Tor | RelayMeshNet Mesh |
|---|---|---|
| **Сеть** | Глобальная (Tor Network) | Локальная mesh |
| **Entry/Exit** | Guard nodes, Exit nodes | Нет exit (всё внутри mesh) |
| **Directory** | Centralized Directory Authorities | DHT (децентрализованный) |
| **Цепи** | Стабильные (~10 мин) | Pool + fallback (адаптивные) |
| **Транспорт** | TCP/IP | LoRa/WiFi mesh |
| **Latency** | Сотни мс | Десятки мс (WiFi) / секунды (LoRa) |

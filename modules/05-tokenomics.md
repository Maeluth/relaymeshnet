# L5: Tokenomics & Reputation 🟡 Required

> **Required.** Без экономических стимулов relay-узлы не мотивированы работать. Сеть технически функционирует, но умирает от фрирайдерства. Токеномика — не «хочу», а «надо чтобы сеть жила».

## Проблема bootstrap

В mesh без интернета не может быть глобального блокчейна (нет консенсуса
между всеми узлами в реальном времени). Нужна экономическая модель,
работающая **offline-first**.

## Mutual Credit System (аналог LETS / Ripple / IOTA lite)

**Принцип**: каждый узел начинает с нулевым балансом и credit limit.
Токены не премайнятся — они возникают при relay и эмиссии confirm-N,
сжигаются при потреблении (transaction burn, см. `13-hybrid-economy.md`).

### Параметры

| Параметр | Значение | Описание |
|---|---|---|
| `CREDIT_BASE` | 0 | Новый узел НЕ получает бесплатных кредитов |
| `CREDIT_LIMIT_FACTOR` | 20 × sqrt(reputation) | Лимит кредитной линии от репутации |
| `RELAY_REWARD` | 1 credit / KB | Вознаграждение за relay 1 KB трафика |
| `SEND_COST` | 1 credit / KB / hop | Стоимость отправки 1 KB через N hop'ов |
| `STORAGE_REWARD` | 0.01 credit / MB / час | Вознаграждение за хранение контента |
| `DHT_MIRROR_REWARD` | 0.001 credit / запись / час | Вознаграждение за DHT-зеркалирование |
| `BURN_RATE` | 0.01 | 1% от каждой транзакции сжигается |
| `DEBT_LIMIT` | -100 | Баланс ниже этого → заморозка исходящих |

### Уровни доступа

Новый узел стартует с нулевым балансом и нулевым credit limit. Единственный
способ начать — confirm-N. С ростом reputation появляется кредитная линия.

```
Баланс:  -100 ─── -50 ─── -10 ─── 0 ─── +50 ─── +100 ───→

Статус:   Заморожен │ Ограничен │ Обычный │ Приоритет │ Премиум

Сообщения: ❌       │ 1/час     │ ∞       │ ∞         │ ∞
Файлы:     ❌       │ ❌         │ до 10МБ │ до 50МБ   │ ∞
Credit:    0        │ 10         │ 50      │ 200        │ 500
```

- Новичок (баланс=0): может отправлять ТОЛЬКО через confirm-N (см. `11-confirm-n-economy.md`)
- Заработал reputation через confirm-N → получает credit limit = 20 × sqrt(reputation)
- Может уйти в минус в пределах credit limit (взять в долг у сети)
- Замороженные могут ТОЛЬКО релеить — это их путь к восстановлению
- Ограниченные — могут отправлять, но медленно
- Приоритетные — их трафик обслуживается в первую очередь
- Нет «перманентного бана» — всегда есть путь назад через relay

## Устойчивость к дефолтам по долгам

**Проблема**: если много узлов уходит в глубокий минус и бросает сеть,
держатели положительных балансов теряют backing. Их RELAY credits обеспечены
долгами, которые никогда не будут возвращены.

**Механизм защиты — transaction burn + emission balance**:

1. Система не обещает 1:1 обеспечение. RELAY credit — это право на будущий
   relay, а не требование к конкретному должнику.

2. **Transaction burn** сжигает 1% от каждой транзакции. При высокой активности
   (много трат = много должников) burn ускоряется → supply сжимается → credit
   становится дороже → стимул релеить и зарабатывать.

3. **Emission через confirm-N** создаёт новые кредиты. При низкой активности
   (мало трат, но много relay-работы) emission поддерживает supply.

4. **Сгоревшие долги не наследуются**: когда должник исключается из сети
   (офлайн > 30 дней с отрицательным балансом), его долг списывается.
   Система не пытается «взыскать» — это mutual credit, а не банковский кредит.

5. Держатели RELAY принимают этот риск. Взамен они получают приоритет
   в relay-очереди и возможность продать RELAY на бирже.

### Почему это работает

Mutual Credit не требует глобального консенсуса. Каждый узел ведёт
свой локальный учёт. При встрече узлы сверяют балансы через gossip.

**Стимулы выровнены**:
- Новичок (баланс 0): отправляет через confirm-N (релеит чужие пакеты) → получает эмиссию кредитов + reputation растёт → появляется credit line (см. `13-hybrid-economy.md`)
- Хочешь отправлять больше → релей чужой трафик (Уровень 2)
- Нарелеил много → высокий баланс → приоритет при отправке
- Не релеишь → уходишь в минус → ограничения
- Ушёл в глубокий минус и бросил сеть → долг списывается, система балансируется transaction burn

## Proof of Relay (PoR)

Криптографическое доказательство выполненного relay:

```go
type RelayReceipt struct {
    RelayNode   string    // peerID релеящего узла
    PacketHash  []byte    // хэш relay-пакета
    BytesRelayed int64    // объём переданных данных
    PoHTimestamp []byte   // PoH-запись момента relay
    Signature   []byte    // подпись relay-узла
}

// Получатель relay (следующий hop) подписывает квитанцию:
receipt = Sign(nextHopPriv, Hash("relay" + packetHash + bytesRelayed + pohTimestamp))
```

Важно: в квитанции нет ни отправителя, ни получателя исходного сообщения.
Только факт «я, узел X, переслал Y байт в момент T». Это сохраняет анонимность.

### Накопление PoR

Узел копит квитанции. Периодически gossip'ит в DHT свой reputation score:

```
reputation = EWMA_total_work / 168 − reputation_demurrage

EWMA_total_work — экспоненциально взвешенная сумма (relay_bytes + 0.01 × storage_byte_hours)
  с half-life = 168 часов (7 дней).

reputation_demurrage — 0.000025% в минуту (≈1% в месяц, сложный процент)
  Применяется КАЖДУЮ минуту, независимо от статуса узла (онлайн/офлайн).
  Офлайн-узлы дополнительно теряют ×2 (≈2% в месяц).

Это означает:
  - Работа, сделанная сегодня, имеет полный вес
  - Работа недельной давности — половинный вес
  - Работа месячной давности — ~1/16 веса + −1% demurrage
  - Узел офлайн неделю: −1% демередж × 2 (офлайн) + EWMA decay
  - Узел офлайн месяц: −4% демередж + EWMA decay — существенная потеря
  - Ключевые узлы не могут "отдыхать" в периоды низкой активности — 
    репутация падает, они теряют приоритет в relay-выборе
```

### Защита от стратегического офлайна

```
Атака: узел работает только в часы пик, выключается ночью.
  → Экономия электричества
  → Сохраняет высокий заработок (relay в пиковые часы)
  → Ослабляет mesh в ночное время

Защита — чисто репутационная (без sandbox/штрафов):
  1. Reputation demurrage ×2 для офлайн-узлов
  2. Упавшая репутация → реже выбирается в relay-цепи → меньше заработок
  3. PoH-возраст: офлайн-узел не генерирует PoH-тики → age gap
  4. Синхронизация времени: роутер сверяет wall-clock с соседями
  5. Gossip-проверка: соседи подтверждают "узел X был онлайн в tick Y"

  Органический механизм: был офлайн → репутация упала → меньше выбирают
  в relay → меньше заработок → стимул не уходить. Без искусственных
  ограничений на relay-вознаграждение.
```

### Вознаграждение за хранение (STORAGE_REWARD)

Узлы, хранящие чанки контентной сети (см. `04-content-storage.md`), получают
STORAGE_REWARD = 0.01 credit / MB / час. Начисление:

1. Узел проходит PoC-челленджи от соседей (доказывает, что хранит чанк)
2. Каждый успешный PoC даёт право на начисление за прошедший период
3. Начисление происходит при gossip-обмене: соседи подтверждают время хранения
4. PoH-записи доказывают, что чанк хранился непрерывно

Пример: узел хранит 500 МБ контента в течение недели (168 часов).
STORAGE_REWARD = 500 × 168 × 0.01 = 840 credits.

### Вознаграждение за DHT-зеркалирование (DHT_MIRROR_REWARD)

Узлы, хранящие DHT-записи СВЕРХ своей XOR-зоны, получают дополнительное
вознаграждение. Это «пассивное хранилище знаний» для узлов с ограниченной памятью:

```
DHT_MIRROR_REWARD = 0.001 credit / запись / час

Стандартный узел (128 MB RAM):
  Хранит ~2000 записей (своя XOR-зона)
  → 0 дополнительного дохода

Узел-зеркало (512 MB RAM + флешка 32 GB):
  Хранит ~50000 записей (вся сеть)
  → (50000 − 2000) × 0.001 = 48 credits / час
  → 1152 credits / день
  → ~35000 credits / месяц
```

**Зачем**:
- Узлы с большим хранилищем монетизируют избыток памяти
- Узлы с малым RAM экономят память (не хранят лишнего)
- Запрос к DHT-зеркалу стоит SEND_COST (как обычное сообщение) — отправитель платит за поиск
- Сеть масштабируется: 10 зеркал покрывают 10000+ узлов без перегрузки каждого

**Механика запроса к зеркалу**:
```
Узел A (64 MB RAM, не хранит peerID_X):
  → DHT lookup "peerID_X" → не найден локально
  → Запрос к ближайшему DHT-зеркалу (известен из gossip):
     {type: DHT_QUERY, key: peerID_X, payment: 0.5 RELAY}
  → Зеркало находит запись → отвечает → получает 0.5 RELAY
  → Узел A потратил 0.5 RELAY, но сэкономил 2 MB RAM
```

## Свободный перевод токенов

Пользователи могут переводить RELAY друг другу:

```
Алиса (баланс: 150) хочет отправить 100 Бобу
Маршрут: [А] → [N1] → [N2] → [N3] → [Б]

После:
  Алиса: 150 - 100 - 1.5(relay_commission) = 48.5
  N1:    +0.5
  N2:    +0.5
  N3:    +0.5
  Боб:   +100  (получает ровно столько, сколько отправили)
```

**Комиссия relay-узлам**:
- Списывается с отправителя (сверх суммы перевода)
- Получатель получает ровно отправленную сумму
- Величина комиссии = сумма(hops × RELAY_COST_PER_HOP)
- Это плата за onion-анонимность транзакции

## Кластеры и backbone

Владелец нескольких узлов (например, 3 узла в 3 корпусах, соединённых
Ethernet поверх электросети) может агрегировать их репутацию:

```go
type Cluster struct {
    Owner    string
    Nodes    []string   // peerID'ы узлов кластера
    Backbone map[string]string  // внутренние каналы (Ethernet)
}

// Репутация кластера = сумма репутаций узлов
func (c *Cluster) Reputation() float64 {
    sum := 0.0
    for _, nodeID := range c.Nodes {
        sum += dht.GetReputation(nodeID)
    }
    return sum
}
```

Кластер получает сверх-пропорциональное преимущество:
- Высокая пропускная способность → высокая репутация
- Внутренняя связь по Ethernet мгновенна → relay быстрее
- Прибыль мотивирует строить инфраструктуру в стратегических местах

## Внутренняя биржа (DEX в DHT) [СТАБ: требует отдельного модуля]

Любой узел может стать обменником. Текущий дизайн — минимальный:

```
ORDER BOOK в DHT (key = hash("exchange"))

SELL:
  0xA1: 1000 RELAY по 0.002 RELAY/KB
  0xB2: 5000 RELAY по 0.003 RELAY/KB

BUY:
  0xC3: 2000 RELAY по 0.0015 RELAY/KB
```

Посредник (exchange node):
- Хранит order book в DHT
- Сводит buy/sell ордера
- Зарабатывает на спреде
- Репутация определяет доверие к посреднику

**Требует проработки**: matching engine, settlement через onion, защита от
front-running, escrow-механика, комиссии exchange-узла, разрешение споров.

## Репутация: BitTorrent-подобная модель

| Механизм | Срабатывает на | Эффект |
|---|---|---|
| **Relay success ratio** | Узел взял пакет и переслал (ACK) | reputation ↑ |
| **Relay failure ratio** | Таймаут без ACK | reputation ↓ |
| **Fraud flag** | Переслан модифицированный пакет (хэш не совпал) | reputation ↓↓↓ |
| **Consumption ratio** | relay_out / relay_in < 0.1 | помечается как "consumer" |

### Продажа reputation-аккаунтов

Приватный ключ узла с высокой репутацией — это актив. Владелец может продать его.
Покупатель получает готовый узел, который сразу выбирают в onion-цепи.

Это не баг, а фича: рынок reputation-аккаунтов означает экономический смысл
инвестировать в железо и uptime.

## Ценообразование RELAY

Цена RELAY/KB определяется равновесием supply/demand:

```
supply_relay = суммарная relay-мощность сети (BW × uptime)
demand_relay = суммарное потребление (сообщения × hops + контент + транзакции)

P(RELAY/KB) = demand_relay / supply_relay
```

### Adoption Loop

```
Фаза 1: Мало узлов, много незанятой мощности → RELAY дёшев
Фаза 2: Дешёвый RELAY → низкий порог входа → приток пользователей
Фаза 3: Много пользователей → relay загружен → RELAY дорожает
Фаза 4: Дорогой RELAY → стимул ставить новые узлы → supply растёт → цена стабилизируется
```

Это саморегуляция: рост спроса → рост цены → стимул ставить новые узлы → рост supply → стабилизация цены.

| Проект | Что заимствуем | Адаптация |
|---|---|---|
| **Solana** | PoH (Proof of History) | Trustless timestamp для PoR |
